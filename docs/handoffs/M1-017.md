## B1a: Existing-key account authorization

- **Linearization point.** Disablement takes effect at the majority-acknowledged commit of the `user:disable` transaction. Each checkout or reconcile request takes effect at the commit of its last fence-bearing transaction. They all write the same user document, so each request is ordered strictly before or strictly after the disablement (M5). See DATABASE_DESIGN §7.2 *Disablement linearization*.
- **No bypass.** Existing-key replays, `409`s and reconcile outcomes previously came from reads outside any transaction. They now come from `authorizedResolve`: one transaction that runs the account fence write plus the registry and `orders` reads, and whose result is used only after a majority commit. Every checkout and reconcile response therefore requires a committed fence.
- **Before vs after.** A request whose fence committed first completes normally, even if the response arrives after the disablement. A request whose fence hasn't committed, including one authenticated earlier and paused, gets `403 ACCOUNT_DISABLED`; it writes nothing and reveals nothing.
- **Not claimed.** `requireAuth`'s status check is only an early filter and does not close the race. Read-only order endpoints rely on it alone, and that is stated explicitly.
- **Preserved.** Orders and `checkoutKeys` are untouched.
- **Docs.** DATABASE_DESIGN §7.2/§7.7, API_CONTRACTS §1.2/§3.3, SECURITY_MODEL T1, BR-18, ADR-002 D11, SYSTEM_ARCHITECTURE sequence.

## B2a: Backup writer barrier

- **Writer inventory:** API, workers (none in V1; any new one must be added first), seed, migrations, maintenance jobs, human operators, and the Atlas TTL monitor (which only touches out-of-scope collections).
- **Barrier:** lock the deploy pipeline; confirm 0 API instances; set every DB user except the backup user to read-only.
- **Verification:** read back the users and roles through the Atlas Admin API before the dump, and again (plus the activity feed) after it. If the barrier can't be established or confirmed, or any change happened during the window, the backup aborts.
- **Fingerprints** are a supplementary check only and are never treated as proof of quiescence.
- **Docs.** DEPLOYMENT_DESIGN §7; BR-19.

## B2b: Fail-closed restore

- The gate record (`controlGate`) is excluded from backups, so a restored database never has one. The API is closed by default.
- The API serves checkout and reconcile only if the record exists, parses, is `open`, and matches its `targetDb`, `clusterId` and `validationId`. This is checked at startup and every 30 s; `MAINTENANCE_MODE=off` can't override a closed gate.
- Only a passing `db:verify --restore --restore-id` writes the gate record. Restores go to a new database name, and the API is pointed at it only after validation.
- A crash, a corrupt record, a mismatched target or a copied record all keep the gate closed.

## B2c: Fingerprint consistency

- **Scope:** a fixed collection list; `controlGate`, `sessions` and `auditLogs` are excluded.
- **Encoding and order:** canonical Extended JSON v2 with keys sorted recursively; documents sorted by `_id`; indexes hashed separately.
- **Versioning:** the script is versioned, and backup and restore must use the same version.
- **Docs.** DATABASE_DESIGN §8.

## Remaining runtime assumptions (not verified)

1. MongoDB M1–M5 hold on `mongo:8` and Atlas; AC-M14-B1c and AC-M16-B1a/b check them.
2. **Atlas Admin API**: on the chosen tier it can change and read back DB user roles, the activity feed records those changes, and a role change takes effect on existing connections promptly. AC-M16-B2a checks this empirically. If it doesn't hold, the fallback dump isn't available and a tier with managed snapshots is required.
3. The hosting platform reports running instances reliably.
4. A full-database canonical fingerprint is affordable at M0 size.
5. A fence write on every replay and reconcile adds some contention on the user document; bounded retries keep it safe, with `UNKNOWN` in the worst case.
