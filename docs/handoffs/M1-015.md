# Handoff — M1-015 Architecture Scope Reduction and Closure (B1, B2)

- Status: **COMPLETE (design only)**. Documentation only; no application code; nothing executed at runtime.
- Date: 2026-11-15
- Baseline: PR [#1](https://github.com/JameThaksin/it-peripheral-store/pull/1) head `cefff1b`
- Input: the B1/B2 descriptions in the M1-015 task. The full M1-014 audit document was not provided.
- Scope: account lifecycle and backup/restore only. The checkout registry, `resolveKey`, the fence semantics and the N1–N3 behavior are preserved. The only change to checkout is one extra first statement, the account fence.

## B1: Account erasure → disablement only

| Requirement | Resolution | Where |
|---|---|---|
| Remove permanent erasure | The erasure procedure and its 60 s wait are deleted. V1 never deletes accounts, orders or registry records | DATABASE_DESIGN §4.5; BR-18; ADR-002 rejected alternatives |
| Disablement only | `user:disable` maintenance command: one transaction sets `isActive: false` and increments `users.accountFence`. Idempotent, bounded retries, audit log | DATABASE_DESIGN §4.1, §7.7 |
| Never delete `checkoutKeys` | Disablement touches only the user document and the audit log | §7.7; AC-M14-B1d, AC-M12-N2d |
| Account state checked inside the transactions | Checkout step 1 and fence step 1: `users.updateOne({ _id, isActive: true }, { $inc: { accountFence } })`; matched 0 → `403 ACCOUNT_DISABLED`, nothing written | §7.2; API_CONTRACTS §1.2, §3.3 |
| Explicit conflict fencing | Disablement and every checkout/reconcile write the same user document. Under snapshot isolation (M5) two such transactions can't both commit, so either the order predates the disablement or the request is rejected. No waiting is assumed | §7.2 feasibility (M5, I5), §7.7; ADR-002 D11 |
| No 60 s delay as safety | No safety property depends on the lifetime limit; it now bounds liveness only | §7.6 |
| Erasure documented as out of scope | Requires a separately reviewed protocol (legal retention, I1/I2 effects, backups, an equivalent fence) | §4.5 |

## B2: Backup and restore

| Requirement | Resolution | Where |
|---|---|---|
| Remove the claim that a live `mongodump` is consistent | Stated explicitly: a live dump reads collections at different times and isn't accepted. `--oplog` isn't relied on | DEPLOYMENT_DESIGN §7 |
| Tier-dependent requirements | M10+: Atlas Cloud Backup snapshots plus continuous backup (required for production). Flex: managed snapshots if documented at setup, else quiesced. M0: quiesced | §7 table |
| Quiesced procedure with verified draining | Scale the API to 0 (confirmed), make the app DB user read-only, then `db:fingerprint` F1 = F2 before the dump and F3 = F1 after it; mismatch → abort. A manifest stores the fingerprint | §7; DATABASE_DESIGN §8 |
| Checkout disabled during restore and validation | API stopped or `MAINTENANCE_MODE=on` (`503 MAINTENANCE` for every non-GET route). A startup gate forces maintenance until `systemState.restore = validated` | §7, §4.1 env vars; API_CONTRACTS §1.2 |
| Verify invariants before reopening | `db:verify --restore`: order ↔ committed record match both ways, no closed record with an order, unique indexes, no TTL, counters/types/stock, and the fingerprint for dumps | DATABASE_DESIGN §8 |
| Limitations of restoring an older backup | Lost orders, closures and disablements; I2 lost for keys closed after the restore point; possibly different answers to customers; disablements re-applied from external incident notes; loss bounded by the RPO | DEPLOYMENT_DESIGN §7 |

## Remaining runtime assumptions (not verified; no code has run)

1. MongoDB behaviors M1–M5 hold on `mongo:8` and Atlas. M5 (same-document write conflict) is new; AC-M14-B1c checks it empirically.
2. Atlas tier features, specifically whether Flex snapshots are documented and restorable and whether M10+ snapshots are consistent, must be confirmed at setup and recorded in ADR-003.
3. The hosting platform can reliably report "zero instances running", and Atlas lets the app DB user be switched to read-only quickly. Both are part of the provider choice.
4. A whole-database fingerprint is affordable at coursework scale (≤ 512 MB on M0). Larger data would need managed snapshots instead.
5. Same-user serialization on `users` (checkout, reconcile, login counters) stays rare enough that bounded retries rarely end in `UNKNOWN`.
6. Operators keep incident notes outside the database, needed to re-apply disablements after a restore.
