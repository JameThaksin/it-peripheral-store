## Resolution matrix: G01–G04

"Resolved" means resolved in the documented design. No acceptance test has been run.

| Finding | Correction | Where | Acceptance |
|---|---|---|---|
| **G01** (HIGH) Absent record treated as proof of failure | Three explicit outcome states: Committed, Not committed, **Unknown**. Unknown arises only after the commit was sent. It triggers bounded read-only reconciliation (majority reads every 250 ms for up to 3 s) and never a fresh attempt or a business error. Still unknown → `503 CHECKOUT_RETRY`, documented as "outcome unknown", with a client rule to retry with the same key. A business error is definitive only for an attempt that threw before commit after inserting the key itself, which is impossible while another transaction for the key is committed or in progress. `E11000` on the key index → reconcile, not retry. | DATABASE_DESIGN §7.2; API_CONTRACTS §1.2, §3.3; BR-14; SYSTEM_ARCHITECTURE §4.3; ADR-002 D2 | AC-G01a, AC-G01b |
| **G02** (HIGH) Seed could reset inventory and counters | Seed is insert-only (`$setOnInsert`, no `$set`). Products are created through the API's transition path, and counters are incremented only when an insert really happened. Existing products, categories and users are never modified. It is safe on a live DB and when two seeds run at once. Counter repair is a transactional maintenance command; `db:reset` is restricted to dev/test. | DATABASE_DESIGN §8; BR-17; ADR-002 D10 | AC-G02a, AC-G02b |
| **G03** (MED) Combined category + activation PATCH | One `applyProductTransition(before, after)` in one transaction, derived from the persisted before-state; an 8-row truth table of counter writes; the product update is conditional on the before-state; concurrent category DELETE serializes on the category document. | DATABASE_DESIGN §7.5; API_CONTRACTS §1.2, §3.4; BR-16; ADR-002 D9 | AC-G03a, AC-G03b |
| **G04** (MED) Revision overflow could block cancellation | `inventoryRevision` is now BSON `long` (Mongoose `BigInt`), never reset, a decimal string in the API, and independent of the stock limit. The stock int32 hard limit is now a conditional restore that fails atomically with `409 INVENTORY_LIMIT` and has a recovery path; the old `500 INVENTORY_OVERFLOW` is removed. | DATABASE_DESIGN §1.1, §4.3, §5, §7.1, §7.4; API_CONTRACTS §1.2, §3.3–3.4; BR-08; ADR-002 D1, D7 | AC-G04, AC-R02e |
