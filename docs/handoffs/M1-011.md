## Design in one paragraph

The checkout transaction still writes a `committed` key record as its first write (unchanged from G01). New: a definitive "no order" answer comes only from the **fence**, which inserts a `closed` **tombstone** for `(userId, key)` with write concern `majority`. The unique index allows either the committed record or the tombstone, never both. The tombstone therefore conflicts with any in-flight checkout transaction for the key (the insert waits for it) and blocks every later one. The fence runs in two places only: after a business error, and in the new owner-only `POST /api/orders/reconcile`. Everything else that can't be decided returns `503 CHECKOUT_RETRY` with outcome `UNKNOWN`. Key age and UUID timestamps are no longer used anywhere.

## Guarantees, kept separate

1. **Exactly-once business effect**: at most one order per `(userId, key)`, ever.
2. **Key retention**: 30 days per record; the key stays on the order permanently.
3. **Unknown outcomes**: only `503` with `UNKNOWN`, resolved by a same-key retry or by reconcile.
4. **Client retries**: same key and identical request, automatic for at most 24 h.
5. **New checkout authorization**: a definitive outcome for the previous key plus an explicit user action.

## Remaining runtime assumptions (not verified; no code has run)

1. **Majority durability.** Commits and tombstones use write concern `majority`, and a majority-acknowledged write is never rolled back. Writes acknowledged only by a deposed primary may roll back, which is why every definitive answer needs a majority acknowledgement or a majority read.
2. **Conflict behaviour.** A non-transactional insert on a unique-index entry held by an open transaction waits (or fails with a retryable error) and is not silently accepted. This is MongoDB's documented behaviour; AC-M10-F1a must confirm it on the target version (`mongo:8`, Atlas).
3. **Transaction lifetime.** `transactionLifetimeLimitSeconds` stays at its 60 s default, so no transaction can commit long after its step-2 timestamp. The 30-day retention relies on this by a wide margin.
4. **Clock.** The API server clock is NTP-synced. A clock step moves window boundaries by the step size only; safety uses no clock.
5. **TTL** deletes after `purgeAt`, never before (it can run late).
6. **Client behaviour.** `localStorage` is available and clients follow rules 1–5. If storage is unavailable or cleared during an `UNKNOWN` outcome, the server stays correct (no duplicate), but the user loses the automatic recovery and must check "My orders". A key is first accepted when the server receives it, so a client that resends a never-committed key long after 24 h, against the rules, could still create that key's single order.
7. **Single API clock source.** One Node service (DEPLOYMENT_DESIGN). With several instances, their clocks must be synced to the same tolerance.
