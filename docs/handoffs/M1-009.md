## R1: Checkout idempotency expiry

| Requirement from the task | Resolution | Where |
|---|---|---|
| Exact 24 h replay guarantee | A four-row decision table evaluated in order: live record (t < commit + 24 h) → replay or `422 REUSED`; order exists for the key → `409 IDEMPOTENCY_KEY_EXPIRED` + `orderNumber`; key issued ≥ 24 h ago → `422 IDEMPOTENCY_KEY_EXPIRED`; otherwise normal checkout. The replay window (from commit) always outlasts the creation window (from key issue), so there is no gap. | DATABASE_DESIGN §7.2 "Exact replay and expiry guarantee"; API_CONTRACTS §3.3; BR-14 |
| No automatic new order after key expiry | Three layers: (1) the server retired-key check (`orders` lookup); (2) the server key-age check (UUID v7 timestamp; future-dated > 5 min → `400`); (3) a permanent unique `orders {userId, idempotencyKey}` index as a database backstop. The old "after 24 h the key is new again" rule was removed everywhere. | DATABASE_DESIGN §4.4, §4.5, §7.2; ADR-002 D2 |
| Client reconciliation / explicit user review | Pending checkout kept in `localStorage`. Automatic same-key retries only within 23 h of issue. After that, the client calls `GET /api/orders?idempotencyKey=` and shows the order, or a "no order was placed, review your cart" message; a new order needs a user click and a new key. | API_CONTRACTS §3.3 (client rules, `GET /api/orders` filter) |
| Preserve unknown-outcome semantics | Unchanged: Committed / Not committed / Unknown, reconciliation, `503 CHECKOUT_RETRY` = "outcome unknown". The new checks are explicitly "not committed, definitive, nothing written". | DATABASE_DESIGN §7.2 outer-control table |
| Acceptance case: committed, record expired before retry | **AC-R1a**, plus AC-R1b (window boundary), AC-R1c (never-committed old key, future key), AC-R1d (client UI), AC-R1e (concurrent expired-key retries). AC-F02c rewritten (it previously required a new order after expiry). | SYSTEM_REQUIREMENTS §7 |

## R2: Product creation

| Requirement from the task | Resolution | Where |
|---|---|---|
| Separate creation from updates in pseudocode | New `createProduct(input, mode)`. `applyProductTransition` is now for updates only, and a missing product returns `404`. | DATABASE_DESIGN §7.5 |
| Insert-if-absent, no null before-state dereference | `updateOne({sku}, {$setOnInsert: …}, {upsert: true})`. The function never reads a before-state; `upsertedCount == 0` → `409 SKU_TAKEN` (API) or skipped (seed). The `before?.` / `?? false` pseudocode was removed. | DATABASE_DESIGN §7.1 create row, §7.5, §8 |
| Category counter and concurrency | `+1` conditional on an active category, only if actually inserted; an inactive create needs an existing category. Any failure aborts the whole transaction, so no orphan product remains. | DATABASE_DESIGN §7.5 |
| Cover active/inactive creation, duplicate SKU, category deactivation races | **AC-R2a** (active/inactive/missing/inactive-category), **AC-R2b** (10 concurrent duplicate SKUs; seed with existing SKU), **AC-R2c** (active and inactive create vs category DELETE). | SYSTEM_REQUIREMENTS §7 |
