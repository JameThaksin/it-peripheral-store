## Feasibility check (done before editing)

Question: can a unique per-user key registry enforce invariants I1–I4 under MongoDB transaction semantics?

The design relies only on these documented behaviors (DATABASE_DESIGN §7.2):

| | Behavior |
|---|---|
| M1 | Unique indexes are enforced across concurrent writers, transactional or not: at most one insert of a given key commits. |
| M2 | A transaction whose commit was never sent never commits; the server aborts it within `transactionLifetimeLimitSeconds` (60 s). |
| M3 | Majority-acknowledged writes survive failover; majority reads return only majority-committed data. |
| M4 | A transaction's writes become majority-committed together; reads in one causally consistent session are monotonic. |

It does **not** rely on a conflicting write waiting for an open transaction, on any scheduling order, or on TTL.

**Result: yes, for safety. Not for liveness.**

| Invariant | Holds? | Why / limit |
|---|---|---|
| I1 At most one order per user/key | Yes | Unique `orders` index plus the unique registry entry inserted in the same transaction (M1) |
| I2 A closed key never creates an order during its closure lifetime | Yes, **while the record exists** | Hence the registry is permanent (no TTL) for the account's lifetime. A restore to an earlier backup is outside the guarantee |
| I3 No false definitive negative | Yes | `CONFIRMED_NOT_COMMITTED` needs a majority-committed closed record **and** a later majority `orders` read with no result (M1, M3, M4) |
| I4 Unresolved never becomes definitive | Yes | Every non-definitive branch maps to `UNKNOWN` |
| Liveness (always a definitive answer) | **No** | Failover, write-concern timeouts, persistent conflicts or a lost abort (≤ 60 s) can keep the answer `UNKNOWN` for a while. The contract says so, and it doesn't promise otherwise |

No weaker fallback contract was needed. The stated limits are documented instead of guarantees MongoDB can't give.

## N1: Closed marker and historical orders

| Requirement | Resolution | Where |
|---|---|---|
| A closed marker alone never proves "no order" | `resolveKey`: majority registry read, **then** a majority `orders` read, in one causally consistent session. Any order → `ORDER_FOUND`, even next to a closed marker (plus an integrity alert) | DATABASE_DESIGN §7.2 |
| Every definitive response accounts for a historical order | Step 0, post-fence, E11000 handling and commit-unknown polling all go through `resolveKey` | §7.2 outer control |
| Majority lookup and read failures | Primary, read concern `majority`, `maxTimeMS` 2 s; any failure → `UNKNOWN` (`503`) | §7.2; API_CONTRACTS §3.3 |
| Outcome semantics preserved | `ORDER_FOUND` / `CONFIRMED_NOT_COMMITTED` / `UNKNOWN`, plus an internal `ABSENT` that is never returned | §7.2; API_CONTRACTS §3.3 |
| Tests | AC-M12-N1a (closed + historical order), N1b (read failures on every path), N1c (every definitive path reads orders) | SYSTEM_REQUIREMENTS §7 |

## N2: Durable closure

| Requirement | Resolution | Where |
|---|---|---|
| Durable, unique per-user registry | `idempotencyKeys` renamed to `checkoutKeys`, unique `(userId, key)`, insert-only (`committed` or `closed`, never updated) | DATABASE_DESIGN §4.5 |
| No TTL during the guarantee | No TTL index and no expiry field. `db:migrate` never creates one; `db:verify` fails if one exists | §4.5, §8; AC-M12-N2a |
| Replay window separate from reuse prevention | `replayUntil` (24 h) only chooses `200` vs `409`; reuse prevention is permanent | §7.2 table; BR-14; AC-M10-F3d |
| Account deletion and retention | Guarantee lifetime = the account's lifetime. Erasure is a maintenance command: disable, wait > 60 s, delete or anonymize orders, delete keys and user. ObjectIds are never reused. Restores are a documented exception | §4.5; DEPLOYMENT_DESIGN §7; AC-M12-N2d |
| Delayed requests can't revive closed keys | Checkout only inserts; the unique entry stays taken | §7.2; AC-M12-N2c |
| Cleanup can't break the guarantee | There is no cleanup path except account erasure; the profiler test asserts only insert and find | AC-M12-N2b |

## N3: MongoDB conflicts

| Requirement | Resolution | Where |
|---|---|---|
| Don't assume waiting | Stated explicitly; the fence handles wait, conflict and timeout | §7.2 *Fence*, §7.6 |
| Conflicts, aborts, timeouts, unknown commits | An explicit outer-control table: `WriteConflict` → bounded retry; error before commit → not committed (M2), with lost aborts covered; unknown commit → `resolveKey` polling only | §7.2 |
| Bounded retries, `UNKNOWN` | Checkout: 3 attempts, 10 s. Fence: 3 inserts, 5 s. Polling: 3 s | §7.2; API_CONTRACTS §3.3 |
| Safety-based tests | AC-M12-N3a (200 randomized interleavings with faults; asserts invariants only), N3b (bounded), N3c (unknown commit), N3d (abandoned transaction). AC-F02d and AC-M10-F1a rewritten to accept any interleaving | SYSTEM_REQUIREMENTS §7 |

## Remaining runtime assumptions (not verified; no code has run)

1. M1–M4 hold on the target versions (`mongo:8` locally, Atlas in production). AC-M12-N3a is the empirical check and should run early in M2.
2. `transactionLifetimeLimitSeconds` stays at 60 s (erasure wait, lost-abort window).
3. The API server clock is NTP-synced (affects only window boundaries, not safety).
4. Registry growth stays small: about 200 bytes per key, bounded by 20 checkouts plus 10 reconciles per user per hour; it is reported weekly.
5. Clients follow the rules in API_CONTRACTS §3.3. If they don't, the server is still safe, but recovery is manual ("My orders").
6. No restore to an earlier backup. A restore voids guarantees given after its restore point (DEPLOYMENT_DESIGN §7).
